## 2. 字段可用性分析

### 2.1 银行流水

**来源说明：** 银行流水在交易日后的第二个工作日由银行生成并提供，反应公司银行账户的实际资金变动。

| 字段 | 完整性 | 说明 |
|------|--------|------|
| 凭证号 | 低 | 示例全部为 `000000000`，无实际凭证号，不可用 |
| 对方账号 | 中 | 部分有账号，部分为空 |
| 交易时间 | 高 | 精确到秒，格式统一 |
| 对方单位 | 中 | 转入方/转出方名称，部分为空（如手续费、POS 清算） |
| 用途 | 低 | 多数为空 |
| 摘要 | 高 | 交易类型描述，如"货款"、"报销"、"跨行汇款手续费" |
| 附言 | 中 | POS 清算流水的附言为商户编号 `100172984575` |
| 转入金额 | 高 | 收入金额 |
| 转出金额 | 高 | 支出金额 |
| 余额 | 高 | 交易后账户余额 |

#### 2.1.1 余额字段的业务重要性

银行流水的"余额"字段是**唯一可以在文件内部进行自洽校验**的字段,也是财务人员制单时**最终核对金额是否一致**的权威依据。它的重要性体现在三个层面:

**1. 逐行连续性(文件级自检)**

每一行的"余额"都应满足如下恒等式:

```text
本行余额 = 上一行余额 + 本行转入金额 − 本行转出金额
```

任何一行不满足,即说明该文件存在以下情形之一:

- **文件截断**:导出过程中被截掉了一部分,常见原因是导出时间窗口跨越午夜或网银会话超时;
- **文件篡改**:有金额被人工改动但忘了同步余额(或反之);
- **多文件拼接**:把不同时间段的银行流水拼接到一个文件里,中间衔接处的余额对不上;
- **导出字段顺序错乱**:网银某些版本导出时"余额"列错位,看似连续实则错位。

**校验口径:严格相等(无容差)。** ForgeFin 在导入时逐行校验 `本行余额 == 上一行余额 + 转入 − 转出`,两侧均为 `Decimal` 严格加减(不经过浮点),因此任何不平都视为真问题,**不应用 ±0.01 元的"四舍五入容差"**。一行不平可能由上述四类问题之一造成,也可能由银行侧合并入账、跨日补录、补贴/立减调整等业务原因造成,统一落入"待财务人员确认"队列。

失败的行**仍会入库**(因为余额字段的存在就是为了发现错误, 而不是阻止导入),
但会写入 `import_errors` 表(`field_name='balance_discontinuity'`),并在导入结果中以黄色警告呈现。

**2. 首末差额自检(整批勾稽)**

文件至少两行有余额时,还会做如下整批自检:

```text
末行余额 − 首行余额  ==  Σ(转入金额) − Σ(转出金额)
```

同 §2.1.1.1 的口径,这里也使用 **Decimal 严格相等**,不平即视为真问题。
若不一致,说明文件级层面存在系统性差异(如某些行的转入/转出被遗漏),而非单行错误。
导入完成后会以 `ImportResult.balance_check_warning` 形式返回警告字符串，前端在"导入结果"中列出。

**3. 财务人员确认(消除告警色的唯一路径)**

由于 §2.1.1.1 / §2.1.1.2 的校验是严格相等的,真实业务中的"非错误性不平"(银行合并入账、跨日补录、补贴/立减、人工标注等)会被标记为 `balance_check_status = 'mismatch'`,在 UI 上以红底高亮显示 — 这是为了**任何不平都先暴露**,而不是替财务人员默认"这笔没事"。

业务规则:

- **不应用容差自动消除告警色** — 任何"消除红底"的决定都**必须**经过财务人员的人工确认,不可由系统默认放过。
- **按 import_batch 整批确认** — 财务人员对账完毕,在「银行流水」页面选中对应批次,点击 **"确认余额"** 按钮,后端将该批次下所有 `bank_flow` 记录的 `balance_confirmed_at` 写为当前时间,并清理 `import_errors` 表中 `field_name='balance_discontinuity'` 的对应错误。
- **确认后的视觉** — 该批次下的 mismatch 行不再显示红底,余额 cell 保持绿色加粗(与 `ok` 行同色),与 `ok` 行视觉一致;`balance_check_status` 仍为 `mismatch`(后端持续暴露不平事实),但前端依据 `balance_confirmed_at IS NOT NULL` 优先选择"已确认"样式。
- **支持撤销** — 在同一位置提供 **"撤销确认"** 按钮,把 `balance_confirmed_at` 清空,UI 红底会重新显示(若该行仍处于 mismatch)。
- **不影响其他来源** — `confirm_balance_batch_cmd` 仅作用于 `source_type = 'bank_flow'` 的记录,不会触碰订单流水 / POS 流水 / 数据汇总。

数据层:`source_records.balance_confirmed_at TEXT`(ISO8601 时间戳,NULL = 未确认);写入/撤销均通过 Tauri 命令 `confirm_balance_batch_cmd(batch_id)` / `unconfirm_balance_batch_cmd(batch_id)` 暴露,返回受影响行数,前端据此刷新列表。

**4. 与凭证系统的最终一致性**

财务人员在制单时，通常的最终核对逻辑是:

- 用银行流水的"末行余额"作为本账期银行存款科目的**期末账面余额**；
- 用"首行余额"作为**期初账面余额**；
- 二者之差(末−首)应等于该账期银行存款科目的**本期借贷净额**(从总账取数)。

如果三方对不上:

- 末行余额 ≠ 银行存款科目期末账面余额 → 通常是漏做了某张银行相关凭证，或凭证金额录错；
- (末−首) ≠ 借贷净额 → 通常是凭证借贷方向记反、或重复制单。

ForgeFin 在导入银行流水时强制保留"余额"字段(每行单独存于 `source_records.balance` 列)，并在导入结果中给出连续性与首末差额两项校验结论,
使财务人员在制单前即可知道"这份银行流水本身是否完整、是否可信"，把"文件问题"和"凭证问题"分开排查。

**主要用途：**
- 银行日记账自动生成
- 银行余额核对
- 识别收入到账与支出付款
- 通过余额连续性自检发现截断、篡改、拼接等问题文件
- 余额连续性校验结果以三色提示:`ok`(绿)/`mismatch`(红,需财务确认)/`skip`(灰,无数据)
- 财务人员整批确认后,`mismatch` 行不再显示红底;支持撤销

**局限性：**
- POS 清算入账为合并金额（T+1 结算，单日多笔合并），无法直接对应单笔交易
- 缺少客户/事由信息，需要配合订单流水和人工汇总
- 不同银行的导出格式可能存在"余额"列名差异(部分银行写"账户余额"、"余额(元)"等),导入时需在 `extract_balance` 中扩充别名

  - 借：对应成本/费用科目
  - 贷：银行存款
- **手续费支出凭证**：
  - 借：财务费用-手续费
  - 贷：银行存款

### 5.7 手续费字段的手工修正与审核规则

手续费金额由系统按 `支付金额 × 费率` 自动计算，但由于以下原因，允许财务人员手工修正：

- **费率四舍五入**：`支付金额 × 费率` 可能产生无限小数（如 `0.25% × 3.00 = 0.0075`），系统按四舍五入保留两位小数后，与银行实际扣收的手续费可能存在 ±0.01 的差异
- **银行侧特殊优惠**：银行对特定卡种或大额交易有封顶手续费或减免政策，系统费率无法覆盖
- **历史数据补录**：导入的历史汇总中手续费已由人工确定，不应被系统自动覆盖

**修正规则：**

1. **手工优先**：数据汇总编辑弹窗中的"手续费"字段始终可手工输入，系统自动计算值仅作为初始填充，不强制锁定
2. **差异标记**：当手工修正值与系统计算值不一致时，该行自动标记 `fee_manual_adjusted` 标识，在列表中该行以黄色高亮显示"费"字标签
3. **快速定位**：数据汇总列表提供"仅显示手续费修正"筛选开关，一键过滤出所有手工修正过的行，方便审核人员逐笔确认
4. **审核路径**：审核人员可在列表中直接定位修正行，点击编辑查看原始计算值与修正值的差异，确认无误后移除高亮标记

**数据层：**

`data_summaries` 表新增 `fee_auto_calculated TEXT` 列（系统自动计算值）和 `fee_manual_adjusted INTEGER DEFAULT 0` 列（1=已手工修正），前端据此展示高亮标记和筛选功能。

## 6. 数据质量问题

1. **银行流水 POS 清算金额合并**：单日多笔 POS 交易合并为一笔银行转入，无法直接拆分，必须依赖订单流水
2. **银行流水中部分支出缺少对方单位**：如跨行汇款手续费未显示收款方，需要人工补录
3. **订单流水缺少客户/业务事由**：无法直接判断收入对应客户或项目，需要结合数据汇总
4. **数据汇总依赖微信群备注**：非结构化来源，无法自动导入，需设计人工补录机制
5. **2026-07-01 清算金额存在 0.45 元差异**：需确认是否由补贴、立减或四舍五入导致
6. **数据汇总表头费率与实际不完全对应**：汇总表中有"借记卡手续费""信用卡手续费""微信/支付宝"三列，但实际仅"微信/支付宝"列有值，借记卡/信用卡交易通过微信/支付宝渠道完成，费率为 0.25%
7. **借记卡/信用卡列无值**：数据汇总表中实际交易通过微信/支付宝渠道完成

## 7. 系统对接建议

### 7.1 数据导入

| 数据源 | 导入方式 | 频率 | 优先级 |
|--------|----------|------|--------|
| 银行流水 | 文件导入（银行网银导出） | 每日 | 高 |
| 订单流水 | 文件导入（工行商户网站导出） | 每日/按需 | 高 |
| 数据汇总 | 手工录入或从模板导入 | 每日 | 中 |
| 微信备注 | 提供补录字段，关联汇总记录 | 实时 | 中 |

### 7.2 系统功能建议

| 功能模块 | 说明 |
|----------|------|
| 银行流水导入 | 支持 TSV 格式，自动识别交易类型 |
| 订单流水导入 | 支持商户网站导出格式 |
| 三方勾稽 | 订单金额 vs 实收 vs 银行流水自动核对 |
| 差异提示 | 标记金额差异，生成待核对任务 |
| 凭证生成 | 基于核对结果自动/半自动生成凭证 |
| 微信备注补录 | 人工补录渠道信息 |

### 7.3 核对机制建议

1. 每日自动比对订单流水实收金额合计与银行流水 POS 清算转入金额
2. 对差异记录生成待核对任务
3. 将数据汇总记录与银行流水、订单流水进行三方勾稽
4. 未匹配的银行流水和订单流水单独列示，提示人工处理
5. **银行流水导入时校验余额连续性**（逐行：`上一行余额 + 转入 − 转出 == 本行余额`，**严格相等、不用容差**，Decimal 精确加减）和首末差额自检（`末行余额 − 首行余额 == Σ(转入) − Σ(转出)`，严格相等），失败行写入 `import_errors`，整批警告通过 `ImportResult.balance_check_warning` 返回，确保制单前即可识别截断、篡改、拼接等问题文件。**任何不平都需要财务人员在「银行流水」页面按批次做人工确认**（`confirm_balance_batch_cmd`）才能消除 UI 红底,确认信息持久化在 `source_records.balance_confirmed_at` 列,支持 `unconfirm_balance_batch_cmd` 撤销

## 9. 结论

### 9.1 数据源定位

当前业务流程中：

- **银行流水**是资金实际变动的权威来源，但单笔 POS 交易已被合并清算，无法单独作为收入确认依据；其"余额"字段是文件内部自洽校验与制单最终一致性的关键依据。
- **订单流水**是最完整的交易级数据来源，包含订单金额、手续费、实收金额、支付方式、结算日期，应作为收入确认和手续费拆分的主要依据。
- **数据汇总**是财务人员整理后的凭证草稿，其中的事由、备注来自微信群等非结构化来源，需要系统提供人工补录和审核机制。

### 9.2 健康管理公司数据特征

健康管理公司（样本企业A）的数据特征：

- **交易频繁、单笔金额小**：POS 收入为主
- **手续费透明**：订单流水中完整记录费率
- **T+1 清算**：需次日核对银行流水
- **微信备注重要**：客户来源、事由依赖人工整理

### 9.3 落地优先级

系统应优先实现银行流水导入、订单流水导入、自动核对与差异提示、以及基于核对结果的凭证生成功能。其中：

- 银行流水导入必须包含余额连续性校验与首末差额自检
- 订单流水作为 POS 收入与手续费拆分的主数据源
- 数据汇总作为人工补录入口，承载微信备注等非结构化信息
